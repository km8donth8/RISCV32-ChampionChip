# ChampionCHIP eXperience Malaysia Edition — Stage 3
## Team 41 (Equipe 41) · RV32I_Zmmul_Xicrc SoC with GPIO & UART · Application: **TollGuard**

This repository integrates the GPIO and UART peripherals of the ChampionCHIP Block Guide
with our Stage 2 multicycle RISC-V core, validates the integration with the **official
GPIO/UART test firmware**, and runs our own application firmware, **TollGuard — a smart
highway toll gantry controller**, validated by a self-checking team testbench.

| Result | |
|---|---|
| Official GPIO & UART test firmware | **PASS** — GPIO `0xA → 0xA` (DATAOUT `0xA0`), UART `0x30 → 0x30`, plus a 2nd loop iteration |
| TollGuard application testbench | **PASS** — 98/98 checks, 7 scenarios × 2 passes, no illegal-instruction halt |
| Synthesis check (Yosys `check -assert`) | **PASS** — both firmware builds |
| Peripheral cost (Yosys generic cells) | GPIO 111 cells (32 FF) · UART 345 cells (72 FF) |
| TollGuard compute latency (last RX byte → first TX byte) | 116 – 196 cycles (2.3 – 3.9 µs @ 50 MHz) |

## 2. How to reproduce

Requirements: Icarus Verilog ≥ 11, GNU Make, Python 3 (+ matplotlib for figures),
RISC-V GNU toolchain (`riscv32-unknown-elf-*` or `riscv64-unknown-elf-*`), optionally Yosys.

```bash
make            # build both firmwares, regenerate vectors, run both testbenches, figures, flat files
make firmware   # only assemble (organisers' Makefile, unchanged)
make sim        # only simulate  -> results/tb_official_fw.log, results/tb_app_fw.log (+ .vcd)
make synth-check
```

The rebuilt official `firmware.txt` is byte-identical to the one published in the
organisers' repository.

## 3. GPIO & UART integration (system architecture)

The peripherals sit on the **same load/store path** as the data memory. The Stage 2 core
interface (`core_address_o`, `core_data_o`, `read_enable`, `write_enable`, `op_size_o`,
`core_data_i`) is unchanged, so the datapath and the 23-state Control Unit needed **no
modification** — firmware reaches the peripherals with ordinary `lw` / `sw`.

| Region | Base | High | Read latency | Notes |
|---|---|---|---|---|
| IMEM | `0x0040_0000` | `0x007F_FFFF` | combinational | fetch + read-only tables (`.rodata`) |
| DMEM | `0x1001_0000` | `0x1001_1FFF` | 1 cycle | byte lanes via LSU (Stage 2) |
| GPIO | `0xF000_0000` | `0xF000_0FFF` | combinational | DATAOUT / DATAIN / DATADIR |
| UART | `0xF100_0000` | `0xF100_0FFF` | combinational | TXDATA / RXDATA / CONTROL |

A load spends two cycles in the Control Unit (`LOAD_REQUEST`, `LOAD_CAPTURE`) and the MDR
is written at the end of `LOAD_CAPTURE`, so both the 1-cycle DMEM and the combinational
peripheral reads are captured correctly. A store is a single `STORE_WRITE` cycle, which
becomes the peripheral write strobe.

**GPIO (`GPIO_equipe41`)** — 8 pins, per-pin direction. `DATADIR[x]=1` enables the output
buffer (pin = `DATAOUT[x]`) and isolates the input (`DATAIN[x]` reads 0); `DATADIR[x]=0`
disables the output and samples the pin through a 2-flip-flop synchroniser. Reset: all
pins inputs. The pins are exposed as a split bus (`gpio_in`, `gpio_out`, `gpio_oe`) so the
block works on FPGA fabric without internal tri-states; `GPIO_Pads_equipe41` provides the
bidirectional `pins_io` bus of Block Guide Figure 1 when needed.

**UART (`UART_equipe41`)** — 8-N-1, LSB first, 115200 baud, full duplex with independent
8-bit TX/RX shift registers, one sample per bit at the bit centre (no oversampling), 2-FF
synchroniser on `rx_i`, start-bit glitch rejection.
`CONTROL[0] TRANSMIT` is set by software and clears itself the next cycle;
`CONTROL[2] TXDONE` is hardware-owned (1 at reset, cleared at start, set at the end of the
stop bit); `CONTROL[1] RXDONE` is set by hardware at the centre of the stop bit and cleared
by software writing 0 (a hardware set in the same cycle wins).
`CLKS_PER_BIT = CLK_FREQ_HZ / BAUD_RATE` — **set `CLK_FREQ_HZ` to the real clock of the
target** (simulation uses 50 MHz → 434 clocks/bit).

**SoC top (`soc_top_equipe41`)** ports: `clk`, `rst_n`, `o_halt`, `gpio_in[7:0]`,
`gpio_out[7:0]`, `gpio_oe[7:0]`, `uart_rx_i`, `uart_tx_o`, `o_pc[31:0]` (the PC is exposed
for the emulator's program-counter register).

### ChipInventor block diagram (mandatory in the report)
1. Import `GPIO_equipe41` and `UART_equipe41` as blocks (and `AddressDecoder_SoC_equipe41`
   if the memory unit is drawn open), or import `MemoryUnit_SoC_equipe41` as one block
   replacing `MemoryUnit_ff_equipe41`.
2. Paste the IMEM contents from `firmware/<fw>/build/firmware.txt` into the IMEM case
   statement (`scripts/gen_imem.py` does the same automatically).
3. Wire `gpio_in/gpio_out/gpio_oe` and `uart_rx_i/uart_tx_o` to top-level pins; use one
   wire colour for the bus (address/data/strobes), one for GPIO and one for UART.

## 4. Official firmware testbench

`tb/tb_official_fw.v` drives the organisers' firmware on the integrated SoC:

* P3-P0 = `0xA` is applied before reset is released, then P7-P4 is checked for `0xA`.
* A bit-accurate UART bus-functional model sends `0x30` on RX at 115200 baud and decodes TX.
* Second iteration (the firmware loops): `0x4B` echo, then GPIO `0x5 → 0x5`. `0x4B`
  (`0100_1011`) is deliberately not a bit-palindrome so bit-order errors are detected.
* Every step has a timeout and prints a clear `[FAIL]`.


## 5. Application definition — TollGuard

| | |
|---|---|
| **System context** | The processor is the controller inside an electronic highway toll gantry. |
| **System input** | Roadside sensors on GPIO (vehicle present, vehicle class, peak-hour flag) and the RFID tag frame on UART (balance, distance, CRC-16). |
| **System processing** | Verify frame integrity with the hardware CRC unit, validate the distance, compute the fare with the multiplier (class tariff × km, +25 % at peak), compare with the balance and debit it. |
| **System output** | Barrier / alarm lamps on GPIO and a receipt on UART (status, fare, new balance). |

### GPIO map (`DATADIR = 0xF0`)

| Pin | Dir | Name | Meaning |
|---|---|---|---|
| P1:P0 | in | CLASS | 0..3 → Class 1 car, Class 2 van, Class 3 lorry, Class 4 taxi |
| P2 | in | PEAK | 1 = peak-hour tariff (+25 %) |
| P3 | in | VEHICLE | 1 = vehicle at the gantry (start trigger) |
| P4 | out | GATE | paid, barrier open |
| P5 | out | LOWBAL | insufficient balance |
| P6 | out | FRAMEERR | frame rejected (CRC error or out of range) |
| P7 | out | READY | idle, waiting for a vehicle |

### UART protocol (all multi-byte fields LSB first, as the emulator sends them)

| Direction | Bytes | Field |
|---|---|---|
| RX (reader → CPU) | 0-3 | BALANCE, uint32, sen (RM 0.01) |
| | 4-5 | DISTANCE, uint16, km |
| | 6-7 | CRC16 of bytes 0-5, CRC-16/CCITT-FALSE (poly `0x1021`, init `0xFFFF`) — same algorithm as our Xicrc unit |
| TX (CPU → host) | 0 | STATUS: 0 OK, 1 LOW_BALANCE, 2 CRC_ERROR, 3 OUT_OF_RANGE |
| | 1-2 | FARE, uint16, sen |
| | 3-6 | BALANCE after the transaction, uint32, sen |

The receipt is 7 bytes, within the emulator's 8-byte return buffer.

### Tariff (illustrative values, stored as a table in IMEM)

| | Class 1 car | Class 2 van | Class 3 lorry | Class 4 taxi |
|---|---|---|---|---|
| Base (sen) | 50 | 100 | 150 | 30 |
| Rate (sen/km) | 12 | 24 | 36 | 6 |

`fare = base + rate × km`; at peak `fare = (fare × 0x14000) >> 16` (×1.25); `km ≤ 1000`.

### Emulator (`./emu`) usage
One `./emu` call is one vehicle, because the emulator resets the processor on every call.
The options follow the firmware protocol order. Full list in `emu/emu_tests.sh`, e.g.:

```bash
# Class 1 car, off-peak, RM50.00, 25 km -> OK, fare 350 sen, balance 4650 sen, GATE
./emu -d 0xF0 -o 0x80 -i 0x08 -t4 0x00001388 -t2 0x0019 -t2 0x8411 -r1 0x00 -r2 0x015E -r4 0x0000122A -o 0x10
```

## 6. Firmware development and processing (`firmware/app/src/main.s`)

1. **Init** — `DATADIR = 0xF0`, clear stale `RXDONE`, `DATAOUT = READY (0x80)`.
2. **Wait for vehicle** — poll `DATAIN` until P3 = 1; latch the sensors (class, peak);
   lamps off (busy).
3. **Receive the frame** — `_uart_getc` polls `RXDONE`, clears it by writing 0 to
   `CONTROL`, reads `RXDATA`. Each of bytes 0-5 is folded into a running CRC **as it
   arrives** with one custom instruction, `crcb s3, a0, s3` (CRC-16 of one byte, seed in
   rs2), while the bytes are assembled into the balance and distance with shifts/ORs.
   Bytes 6-7 form the received CRC. Because the CRC is computed on the fly, it is ready the
   moment the last byte arrives.
4. **Validate** — running CRC ≠ received CRC → `CRC_ERROR`; km > 1000 → `OUT_OF_RANGE`.
5. **Tariff** — base and rate are loaded from a table in IMEM indexed by class;
   `mul t3, t3, s5` (rate × km, Zmmul) + base.
6. **Peak surcharge** — ×1.25 in Q16.16 fixed point needs a 64-bit product, formed with
   `mul` (low word) and `mulhu` (high word) and recombined as `(hi << 16) | (lo >> 16)`.
7. **Charge** — `bltu balance, fare` → `LOW_BALANCE` (balance untouched), otherwise
   `balance − fare` → `OK`.
8. **Respond** — lamps first (GATE / LOWBAL / FRAMEERR), then the 7-byte receipt through
   `_uart_putc` (polls `TXDONE`, writes `TXDATA`, read-modify-write of `CONTROL` to set
   `TRANSMIT` without clearing `RXDONE`).
9. **Wait for the vehicle to leave** (P3 = 0), then return to READY.

`crcb` is emitted with `.insn r 0x33, 0, 0x40, rd, rs1, rs2` (opcode `0110011`, funct3
`000`, funct7 `1000000`) — the Stage 2 Xicrc encoding, so the unmodified organisers'
Makefile assembles it. Firmware size: 113 words (105 instructions + an 8-word tariff table).

## 7. Custom firmware validation — team testbench

`tb/tb_app_fw.v` plays the roadside: vehicle sensors on P3-P0, the RFID reader on UART RX,
and it checks the receipt and the lamps against `tb/app_vectors.vh`, generated by the
Python reference model `scripts/tollguard_model.py` (which also generates the `./emu`
commands, so the testbench and the emulator tests cannot drift apart).

* **Pass A, emulator style** — reset before every vehicle, then exactly the `./emu`
  sequence: READY lamp → trigger → 8-byte frame → 7-byte receipt → lamps.
* **Pass B, continuous gantry** — one reset, vehicles back-to-back; also checks that the
  lamps are held while the vehicle is present and READY returns after it leaves.
* A probe measures the latency from the last received byte to the first transmitted byte.
* A monitor fails the test if the core ever enters HALT / ILLEGAL.

| # | Scenario | GPIO in | Status | Fare (sen) | New balance (sen) | Lamps |
|---|---|---|---|---|---|---|
| 0 | Car, off-peak, RM50.00, 25 km | `0x08` | OK | 350 | 4650 | `0x10` |
| 1 | Van, peak, RM100.00, 120 km | `0x0D` | OK | 3725 | 6275 | `0x10` |
| 2 | Lorry, RM10.00, 80 km | `0x0A` | LOW_BALANCE | 3030 | 1000 | `0x20` |

## 8. Notes

* **Clock:** simulation uses a 50 MHz clock. For the AWS stage, set `CLK_FREQ_HZ` on
  `soc_top_equipe41` to the FPGA clock so the UART keeps 115200 baud.
* **GPIO output on input pins:** `gpio_out` is `DATAOUT & DATADIR`, so pins configured as
  inputs read 0 on the output bus — consistent with the emulator examples
  (`-d 0xF0 -i 0x02 -o 0x20`).
* **Code origin:** the core is our Stage 2 design. The official test firmware and the
  firmware builder (Makefile, linker script, `bin2rom.py`) are the organisers' files and are
  used unmodified. All other RTL, firmware, testbenches and scripts in this repository were
  written for this stage by Team 41.
